# Архитектурное решение по кешированию

## Контекст
У «Александрита» есть две явные проблемы, связанные с производительностью:
1. Операторы жалуются на медленную загрузку первой страницы MES со списком заказов.
2. Рост числа заказов усиливает нагрузку на систему, а бизнесу нужно ускорить прохождение заказов и работу операторов.

Из описания видно, что самая болезненная точка — это сценарий чтения списка заказов в MES. Команда уже пробовала фильтрацию и пагинацию, но это не помогло. Значит, проблема глубже:
- тяжёлые запросы к операционной БД;
- отсутствие оптимизированной read-модели;
- высокая конкуренция чтения и записи;
- отсутствие кеширования для часто запрашиваемых данных.

Поэтому основной кандидат на кеширование — **операция чтения списка новых и активных заказов в MES**, особенно для первой страницы dashboard операторов.

## Что имеет смысл кешировать

### 1. Список заказов для dashboard MES
Это главный кандидат, потому что:
- запрос выполняется часто;
- данные нужны многим операторам;
- операторам особенно важны самые новые заказы;
- данные меняются часто, но не непрерывно каждую миллисекунду;
- допустима очень небольшая задержка актуализации при правильной инвалидации.

### 2. Агрегаты по статусам для dashboard
Например:
- количество заказов в статусах;
- число новых заказов, доступных для взятия в работу;
- число заказов в расчёте стоимости;
- число заказов в упаковке.

Это хорошие кандидаты, потому что:
- они часто читаются;
- дорого пересчитывать их на лету;
- они хорошо подходят для отдельного ключевого кеша.

### 3. Справочные данные и редко меняющиеся словари
Например:
- статусы;
- типы изделий;
- настройки фильтров;
- справочники для UI.

Это вторичный кандидат. Такой кеш полезен, но не решает главную боль бизнеса.

## Что не стоит кешировать в первую очередь
1. **Результат расчёта стоимости как основной объект оптимизации** — проблема здесь не только в чтении, а в самой тяжёлой вычислительной операции. Кеширование может помочь только в частных случаях повторного расчёта одинаковых моделей, но это не главный быстрый выигрыш.
2. **Критичные транзакции смены статуса заказа** — запись должна идти в основное хранилище как источник истины.
3. **Данные, требующие абсолютной консистентности в реальном времени**, если нет надёжной стратегии инвалидации.

## Мотивация

### Почему нужно внедрить кеширование
1. **Ускорить работу операторов MES.**  
   Сейчас первая страница MES загружается медленно. Кеширование позволит быстро отдавать список новых заказов и агрегаты по статусам.

2. **Снизить нагрузку на операционную БД.**  
   Частые одинаковые запросы на чтение перестанут постоянно нагружать основную базу.

3. **Улучшить масштабируемость.**  
   При росте числа операторов и заказов кеш позволит дольше обходиться без радикального масштабирования БД.

4. **Сократить время реакции операторов на новые заказы.**  
   Это напрямую влияет на скорость запуска заказа в производство.

5. **Создать основу для read-optimized архитектуры.**  
   Кеширование может стать промежуточным шагом к полноценной read-модели.

### Какие элементы системы включаются в кеширование
- список заказов для первой страницы MES;
- выборки по статусам и фильтрам, которые используются чаще всего;
- агрегаты по статусам для dashboard;
- справочные данные для UI.

## Предлагаемое решение

### Выбранный тип кеширования
Основной выбор — **серверное кеширование**.

### Почему серверное, а не клиентское
**Серверное кеширование подходит лучше, потому что:**
1. Одни и те же данные читают многие операторы.
2. Нужно разгрузить backend и БД, а не только ускорить один браузер.
3. Клиентское кеширование не решит проблему тяжёлых запросов на стороне сервера.
4. Сервер может централизованно управлять TTL, инвалидацией и консистентностью.

**Почему клиентское кеширование недостаточно:**
- помогает только конкретному пользователю;
- не снижает существенно нагрузку на БД при множестве операторов;
- сложнее контролировать актуальность данных между пользователями.

### Где внедрять кеш
Предлагается внедрить кеш между backend MES и основной БД.

### Технология
Рекомендуемая технология — **Redis**.

**Почему Redis:**
- быстрый in-memory доступ;
- поддержка TTL;
- удобная работа с ключами и структурами данных;
- зрелая технология для серверного кеширования;
- подходит для хранения списков, агрегатов и небольших read-моделей.

## Какой паттерн кеширования использовать
Для списка заказов и агрегатов предлагается использовать **Cache-Aside**.

### Почему выбран Cache-Aside
1. Хорошо подходит для read-heavy сценариев.
2. Прост в реализации и внедрении в существующую архитектуру.
3. Позволяет постепенно вводить кеш без полной переработки модели данных.
4. Даёт контроль над тем, какие именно запросы кешируются.
5. Хорошо сочетается с программной инвалидацией при смене статусов заказа.

### Почему не Write-Through
**Write-Through** хуже подходит, потому что:
- увеличивает сложность записи;
- требует синхронного обновления кеша при каждой операции;
- не все данные, которые пишутся, обязательно будут часто читаться;
- для текущей задачи важнее ускорить чтение, чем строить write-optimized кеш.

### Почему не Refresh-Ahead как основной паттерн
**Refresh-Ahead** полезен только как дополнительная оптимизация для горячих ключей, но не как базовый паттерн, потому что:
- требует более сложной логики прогнозирования горячих данных;
- может обновлять данные, которые уже не нужны;
- на первом этапе важнее простота и управляемость.

### Итог по паттерну
Базовый вариант:
- **Cache-Aside** для списков заказов и агрегатов;
- при необходимости позже добавить **Refresh-Ahead** для самых горячих ключей dashboard.

## Какие сущности участвуют в кешировании
1. **MES Frontend** — запрашивает список заказов.
2. **MES Backend** — проверяет кеш и при необходимости читает БД.
3. **Redis** — хранит кешированные списки и агрегаты.
4. **MES Database** — источник истины.
5. **Order Status Update flow** — инвалидирует или обновляет кеш при изменении статуса.

## Ключи кеша
Примеры ключей:
- `mes:orders:list:status=NEW:page=1:size=20:sort=created_desc`
- `mes:orders:list:status=MANUFACTURING_STARTED:page=1:size=20`
- `mes:dashboard:counts`
- `mes:orders:latest`
- `mes:reference:statuses`

Важно ограничить число кешируемых комбинаций фильтров. На первом этапе стоит кешировать только:
- самые частые статусы;
- первую страницу;
- сортировку по дате создания/обновления;
- агрегаты dashboard.

## Диаграмма последовательности
Ниже — текстовое представление sequence diagram, которое можно перенести в PlantUML / draw.io.

### 1. Чтение списка заказов
```text
Operator -> MES Frontend: открыть dashboard
MES Frontend -> MES Backend: GET /orders?status=NEW&page=1
MES Backend -> Redis: GET mes:orders:list:status=NEW:page=1:size=20
alt cache hit
    Redis -> MES Backend: cached response
    MES Backend -> MES Frontend: список заказов
else cache miss
    MES Backend -> MES Database: SELECT orders ...
    MES Database -> MES Backend: result set
    MES Backend -> Redis: SET key value TTL
    MES Backend -> MES Frontend: список заказов
end
```

### 2. Изменение статуса заказа
```text
Operator -> MES Frontend: взять заказ в работу
MES Frontend -> MES Backend: POST /orders/{id}/start
MES Backend -> MES Database: UPDATE order status
MES Database -> MES Backend: success
MES Backend -> Redis: DEL affected list keys
MES Backend -> Redis: DEL mes:dashboard:counts
MES Backend -> MES Frontend: success response
```

## Описание процесса кеширования

### Сценарий чтения
1. Оператор открывает первую страницу MES.
2. Backend MES формирует нормализованный ключ кеша.
3. Если данные есть в Redis, backend сразу возвращает результат.
4. Если данных нет, backend читает БД, сериализует результат и кладёт его в Redis.
5. Следующие запросы получают данные из кеша.

### Сценарий записи
1. При изменении статуса заказа backend сначала пишет в БД.
2. После успешной записи backend инвалидирует связанные ключи кеша.
3. Следующий запрос на чтение пересобирает кеш из актуальных данных.

## Стратегия инвалидации кеша
Основная стратегия — **программная инвалидация по ключу** в сочетании с **коротким TTL**.

### Почему выбран этот вариант
1. Статусы заказов меняются часто, поэтому нужен контроль актуальности.
2. Только TTL недостаточен: операторы могут видеть устаревшие данные слишком долго.
3. Только полная очистка кеша слишком груба и создаёт лишнюю нагрузку.
4. Инвалидация по ключу позволяет удалять только затронутые выборки.

### Как это будет работать
При изменении статуса заказа:
- удаляются ключи списков, в которые заказ входил раньше;
- удаляются ключи списков, в которые заказ теперь должен попасть;
- удаляется ключ агрегатов dashboard;
- при необходимости обновляется кеш карточки конкретного заказа.

### TTL
Рекомендуемый TTL:
- для списков dashboard: **15–30 секунд**;
- для агрегатов по статусам: **10–20 секунд**;
- для справочников: **часы или сутки**.

TTL нужен как страховка на случай, если программная инвалидация не сработала.

## Почему другие стратегии инвалидации подходят хуже

| Стратегия | Плюсы | Минусы | Вывод |
|---|---|---|---|
| Только временная (TTL only) | Простая реализация | Риск устаревших данных для операторов | Недостаточно |
| Полная очистка кеша | Простая логика | Сильные скачки нагрузки, низкая эффективность | Слишком грубо |
| Инвалидация по ключу | Точнее и эффективнее | Требует продуманной схемы ключей | Лучший базовый вариант |
| Обновление кеша вручную при записи | Высокая актуальность | Сложнее поддерживать, риск ошибок | Можно использовать точечно |
| Event-driven invalidation | Хорошо масштабируется | Сложнее внедрять на первом этапе | Хорошо как следующий шаг |

## Дополнительный сравнительный анализ решений

| Решение 1: Redis Cache-Aside | Решение 2: Read replica + минимальный кеш |
|---|---|
| **Описание**: Redis хранит горячие списки и агрегаты dashboard | **Описание**: чтение переносится на read replica, кеш используется ограниченно |
| **Плюсы**: быстрый отклик, сильная разгрузка БД, быстрый эффект | **Плюсы**: меньше риск устаревших данных, проще логика приложения |
| **Минусы**: нужна инвалидация, риск stale data | **Минусы**: не решает полностью проблему тяжёлых повторяющихся запросов |
| **Когда подходит**: если главная цель — резко ускорить dashboard | **Когда подходит**: если основная проблема в конкуренции чтения и записи |

### Заключение по вариантам
Наиболее подходящее решение для текущей ситуации — **Redis + Cache-Aside**. Оно даёт быстрый и заметный эффект именно в том сценарии, который сейчас болит сильнее всего: чтение списка заказов в MES. Read replica может быть полезным дополнением позже, но как самостоятельная мера она, скорее всего, не даст такого же ускорения.

## Риски и ограничения
1. Кеширование не исправит плохие SQL-запросы само по себе — запросы и индексы всё равно нужно оптимизировать.
2. Есть риск устаревших данных, если инвалидация реализована неправильно.
3. При слишком большом числе комбинаций фильтров кеш может стать малоэффективным.
4. Нельзя превращать Redis в источник истины — основным хранилищем остаётся БД.
5. При сбое Redis система должна продолжать работать через fallback на БД.

## План внедрения

### Этап 1. Анализ и подготовка
- профилировать запросы dashboard MES;
- определить топ-5 самых частых запросов;
- спроектировать схему ключей кеша;
- определить TTL и правила инвалидации.

### Этап 2. MVP
- развернуть Redis;
- внедрить Cache-Aside для первой страницы списка заказов;
- внедрить кеш агрегатов dashboard;
- добавить метрики cache hit / miss / invalidation.

### Этап 3. Расширение
- добавить кеширование других горячих фильтров;
- при необходимости добавить Refresh-Ahead для самых горячих ключей;
- связать кеширование с мониторингом и алертингом.

### Этап 4. Контроль результата
- сравнить latency до и после внедрения;
- измерить снижение нагрузки на БД;
- проверить, сократилось ли время реакции операторов на новые заказы.

## Метрики успеха решения
1. Время загрузки первой страницы MES.
2. p95/p99 latency запроса списка заказов.
3. Нагрузка на БД по чтению.
4. Cache hit ratio.
5. Время от появления заказа до взятия его оператором в работу.

## Итог
Для «Александрита» имеет смысл в первую очередь кешировать чтение списка заказов и агрегатов dashboard в MES. Лучшее стартовое решение — серверное кеширование на Redis с паттерном Cache-Aside и программной инвалидацией по ключу в сочетании с коротким TTL. Это решение напрямую адресует главную боль операторов, снижает нагрузку на БД и даёт быстрый бизнес-эффект без радикальной перестройки всей архитектуры.
