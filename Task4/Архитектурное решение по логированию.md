# Архитектурное решение по логированию

## Контекст
Система «Александрит» состоит из онлайн-магазина, CRM, MES, RabbitMQ и баз данных. Сейчас разбор ошибок и нестандартных ситуаций происходит в основном со слов клиентов и операторов. Это означает, что:
- команда не видит полную картину происходящего внутри сервисов;
- поиск причины инцидента занимает много времени;
- поддержка и разработчики тратят много ресурсов на ручное восстановление цепочки событий;
- невозможно быстро отличить единичную ошибку пользователя от системной деградации.

Для решения этой проблемы нужно внедрить централизованное структурированное логирование и превратить его из «склада текстовых сообщений» в инструмент анализа и расследования инцидентов.

## Какие системы нужно покрыть логированием
Логирование нужно внедрять во всех системах, через которые проходит заказ или где может возникнуть техническая причина деградации.

### 1. Онлайн-магазин
Нужно собирать логи:
- backend приложения;
- интеграционных вызовов;
- ошибок загрузки 3D-моделей;
- операций создания и отправки заказа.

### 2. CRM
Нужно собирать логи:
- backend приложения;
- обработки входящих сообщений;
- смены статусов заказа;
- ошибок создания/обновления заказа;
- действий менеджеров по подтверждению и закрытию заказа.

### 3. MES
Нужно собирать логи:
- backend приложения;
- расчёта стоимости;
- чтения списка заказов для dashboard;
- действий операторов;
- смены производственных статусов;
- ошибок интеграции и производственных операций.

### 4. RabbitMQ и интеграционный слой
Нужно собирать:
- системные логи брокера;
- логи publisher/consumer приложений;
- ошибки доставки и обработки сообщений;
- события retry / DLQ / reject / nack.

### 5. API для внешних партнёров
Нужно собирать:
- входящие запросы;
- ошибки валидации;
- ошибки авторизации и квотирования;
- результаты приёма заказа;
- correlation id и client id.

### 6. Инфраструктурные компоненты
Нужно собирать:
- системные логи VM/инстансов;
- логи reverse proxy / ingress / load balancer, если используются;
- логи контейнерной платформы в будущем;
- логи БД по ошибкам, медленным запросам и отказам подключения.

## Какие логи нужно собирать с уровнем INFO
Ниже — минимальный обязательный набор бизнес- и технически значимых логов уровня INFO.

### 1. События жизненного цикла заказа
1. Создание заказа.
2. Загрузка 3D-модели.
3. Отправка заказа пользователем.
4. Приём заказа через API партнёра.
5. Расчёт стоимости начат.
6. Расчёт стоимости завершён.
7. Заказ создан в CRM.
8. Заказ подтверждён к производству.
9. Заказ взят оператором в работу.
10. Производство завершено.
11. Упаковка начата.
12. Заказ отправлен.
13. Заказ закрыт.

**Что логировать:**
- `timestamp`
- `service`
- `environment`
- `order_id`
- `correlation_id`
- `customer_id` в псевдонимизированном виде
- `partner_client_id` для B2B
- `from_status`
- `to_status`
- `actor_type` (`customer`, `manager`, `operator`, `system`)
- `actor_id` при необходимости
- `result`

### 2. Интеграционные события
1. Публикация сообщения в RabbitMQ.
2. Получение сообщения consumer’ом.
3. Успешная обработка сообщения.
4. Повторная обработка сообщения.
5. Перемещение сообщения в DLQ.

**Что логировать:**
- `timestamp`
- `service`
- `queue_name`
- `exchange`
- `routing_key`
- `message_id`
- `correlation_id`
- `order_id`
- `attempt`
- `result`
- `processing_time_ms`

### 3. Пользовательские и операторские действия
1. Открытие списка заказов в MES.
2. Применение фильтра по статусу.
3. Взятие заказа оператором.
4. Подтверждение заказа менеджером.
5. Ручное закрытие заказа.

**Что логировать:**
- `timestamp`
- `service`
- `user_role`
- `user_id`
- `action`
- `order_id`
- `filter_params`
- `result`
- `duration_ms`

### 4. Технические события
1. Старт и остановка приложения.
2. Успешное подключение к БД / брокеру / внешнему сервису.
3. Выполнение критичного фонового job.
4. Выполнение расчёта стоимости.
5. Выполнение медленного запроса, если он превысил порог, но завершился успешно.

**Что логировать:**
- `timestamp`
- `service`
- `component`
- `operation`
- `duration_ms`
- `result`
- `trace_id`

## Будут ли использоваться другие уровни логирования
Да, кроме INFO нужно использовать и другие уровни.

### DEBUG
Использовать ограниченно:
- только временно при расследовании сложных инцидентов;
- только для конкретного сервиса/компонента;
- не включать глобально на проде надолго.

**Примеры:**
- подробности сериализации/десериализации сообщений;
- промежуточные шаги расчёта стоимости;
- детали retry-логики.

### WARN
Использовать для ситуаций, когда операция завершилась, но есть риск деградации.

**Примеры:**
- повторная попытка обработки сообщения;
- превышение порога длительности запроса;
- временная недоступность внешней зависимости с успешным fallback;
- подозрительно большой размер файла модели.

### ERROR
Использовать для ошибок, требующих внимания команды.

**Примеры:**
- не удалось создать/обновить заказ;
- не удалось обработать сообщение;
- ошибка расчёта стоимости;
- ошибка подключения к БД или RabbitMQ;
- необработанное исключение в API.

### FATAL / CRITICAL
Если стек логирования поддерживает такой уровень, использовать для событий, после которых сервис не может продолжать работу.

**Примеры:**
- приложение не стартовало;
- потеря критичной конфигурации;
- невозможность подключиться к обязательной зависимости при старте.

## Мотивация

### Почему нужно внедрить логирование
1. **Сократить время расследования инцидентов.**  
   Сейчас команда восстанавливает картину по словам клиента. Централизованные логи позволят быстро увидеть, что произошло в системе.

2. **Снизить нагрузку на поддержку.**  
   Поддержка сможет быстрее отвечать на вопрос «что случилось с заказом».

3. **Повысить надёжность интеграций.**  
   Логи публикации и обработки сообщений помогут выявлять потери, дубли и ошибки интеграции.

4. **Ускорить поиск причин деградации MES.**  
   Можно будет анализировать медленные запросы, тяжёлые операции и действия операторов.

5. **Создать основу для аудита и безопасности.**  
   Логи помогут отслеживать критичные действия пользователей и систем.

### Технические и бизнес-метрики, на которые повлияет внедрение логирования
1. **MTTR** — сократится за счёт более быстрого поиска причины.
2. **Время ответа поддержки по инциденту** — сократится.
3. **Доля инцидентов с неизвестной причиной** — снизится.
4. **Доля потерянных/необработанных заказов** — снизится после выявления проблемных мест.
5. **SLA по обработке заказов и API** — улучшится за счёт более быстрой реакции.

## Что внедрять в первую очередь
Команда не сможет покрыть всё сразу, поэтому нужен порядок внедрения.

### Первая очередь
1. **MES backend**  
   Это главный узкий узел: расчёт стоимости, dashboard операторов, производственные статусы.

2. **CRM backend**  
   Здесь создаются и подтверждаются заказы, а также закрывается жизненный цикл.

3. **Интеграция через RabbitMQ**  
   Это критичная зона риска потери сообщений.

4. **Внешний API для партнёров**  
   После открытия API компания начала терять контракты, поэтому этот канал нужно быстро сделать прозрачным.

### Вторая очередь
5. **Онлайн-магазин backend**
6. **Базы данных и инфраструктурные компоненты**
7. **Фронтенд-клиенты в части клиентских ошибок и correlation id**, если это потребуется.

### Почему именно так
Приоритет определяется влиянием на потерю заказов и просрочки. Сначала нужно покрыть те системы, где заказ чаще всего может зависнуть или потеряться и где уже есть явные жалобы бизнеса.

## Предлагаемое решение

### Выбранный подход
Предлагается внедрить централизованное структурированное логирование со следующим стеком:
- **OpenSearch** как платформа хранения и поиска логов;
- **OpenSearch Dashboards** для визуализации и анализа;
- **Fluent Bit** как агент сбора и доставки логов;
- при необходимости **Vector** или **Logstash** для более сложных пайплайнов обработки;
- интеграция с Alertmanager / webhook / почтой / мессенджером для алертинга.

### Почему OpenSearch
- открытая лицензия и отсутствие vendor lock-in уровня проприетарных решений;
- зрелая экосистема для поиска и анализа логов;
- подходит для структурированных JSON-логов;
- хорошо сочетается с observability-стеком.

### Как будет устроено решение
1. Все backend-сервисы пишут логи в **JSON-формате** в stdout/file.
2. Агент сбора логов (Fluent Bit) забирает логи с инстансов/контейнеров.
3. На этапе доставки добавляются общие поля:
   - `service`
   - `environment`
   - `host`
   - `trace_id`
   - `correlation_id`
4. Логи отправляются в OpenSearch.
5. Для каждой системы создаются отдельные индексы или data streams.
6. В OpenSearch Dashboards настраиваются:
   - поиск по `order_id`, `correlation_id`, `trace_id`;
   - дашборды по ошибкам;
   - дашборды по интеграциям;
   - дашборды по медленным операциям.

### Какие компоненты нужно внедрить или доработать
1. Добавить структурированное логирование в Java backend онлайн-магазина.
2. Добавить структурированное логирование в Java backend CRM.
3. Добавить структурированное логирование в C# backend MES.
4. Добавить единый формат логов и обязательные поля.
5. Добавить `trace_id` и `correlation_id` во все логи.
6. Развернуть OpenSearch cluster.
7. Развернуть OpenSearch Dashboards.
8. Развернуть Fluent Bit на всех инстансах.
9. Настроить пайплайны парсинга, нормализации и redaction чувствительных данных.
10. Настроить алерты и saved searches.

### Что отразить на схеме
На диаграмме нужно показать:
- OpenSearch cluster;
- OpenSearch Dashboards;
- Fluent Bit / log collector;
- связи от онлайн-магазина, CRM, MES, RabbitMQ и инфраструктуры к log collector;
- связь log collector → OpenSearch;
- связь пользователей поддержки/разработки → OpenSearch Dashboards.

## Политика безопасности

### Работа с чувствительными данными
1. Не логировать:
- пароли;
- токены;
- платёжные данные;
- полные ФИО и адреса;
- содержимое 3D-файлов;
- персональные данные без необходимости.

2. Использовать:
- маскирование чувствительных полей;
- псевдонимизацию customer id;
- redaction на уровне приложения и пайплайна доставки.

### Доступ к логам
1. Доступ только по корпоративной учётной записи.
2. Ролевой доступ:
- поддержка — чтение ограниченного набора индексов;
- разработчики — чтение технических логов своих сервисов;
- DevOps/SRE — администрирование платформы;
- администраторы безопасности — аудит доступа.

3. Все соединения — только по TLS.
4. Доступ извне — только через VPN / bastion / reverse proxy с аутентификацией.
5. Все действия пользователей в системе логов должны сами аудироваться.

## Политика хранения

### Разделение индексов
Рекомендуется хранить логи раздельно:
- `logs-shop-*`
- `logs-crm-*`
- `logs-mes-*`
- `logs-rabbitmq-*`
- `logs-api-*`
- `logs-infra-*`
- `logs-security-audit-*`

### Сроки хранения
Предлагаемый базовый вариант:
- INFO/WARN — 30 дней горячего хранения;
- ERROR/CRITICAL — 90 дней;
- security/audit logs — 180 дней или по требованиям компании;
- агрегированные архивы — дольше, если это нужно для расследований и compliance.

### Оценка размера
Точный размер нужно уточнить после пилота, но подход такой:
1. На пилоте измерить средний объём логов в день по каждой системе.
2. Умножить на retention и коэффициент репликации.
3. Отдельно оценить всплески при росте B2B API.

### Lifecycle policy
- горячее хранение для свежих логов;
- перевод старых логов в более дешёвое хранилище;
- автоматическое удаление по retention policy.

## Как превратить сбор логов в систему анализа логов

### 1. Настроить алертинг
Да, алертинг нужен.

Нужно алертить на:
- рост ERROR по сервису;
- рост ошибок обработки сообщений;
- появление записей о DLQ;
- всплеск 5xx по API;
- рост медленных запросов MES dashboard;
- ошибки расчёта стоимости;
- массовые ошибки авторизации/валидации API;
- отсутствие ожидаемых INFO-событий по критичному процессу.

### 2. Искать аномалии
Да, поиск аномалий нужен.

Примеры:
- резкий рост числа заказов за секунду/минуту;
- резкий рост ошибок одного типа;
- необычный рост повторных попыток обработки сообщений;
- всплеск запросов от одного `client_id`;
- резкое увеличение времени расчёта стоимости.

### 3. Построить сценарии расследования
Нужно подготовить saved searches / dashboards:
- поиск всех событий по `order_id`;
- поиск всех событий по `correlation_id`;
- поиск всех ошибок по `message_id`;
- поиск всех действий конкретного оператора/менеджера;
- поиск всех медленных операций по MES.

### 4. Связать логи с трейсингом и метриками
- в логах должен быть `trace_id`;
- из трейса должен быть переход к логам;
- из алерта по метрике должен быть переход к логам и трейсам.

### Обоснование выбора
**Почему OpenSearch подходит лучше всего:**
1. Даёт сильный полнотекстовый поиск и аналитику.
2. Подходит для структурированных JSON-логов.
3. Не требует проприетарной лицензии уровня Splunk.
4. Лучше подходит для расследования сложных инцидентов, чем Loki, если нужен богатый поиск по полям и тексту.
5. Хорошо масштабируется и широко используется.

### Минусы OpenSearch
- требует отдельной эксплуатации и настройки;
- дороже и сложнее Loki в простых сценариях;
- нужен контроль объёма хранения и индексации.

## План внедрения

### Этап 1. Базовый пилот
- определить единый JSON-формат логов;
- внедрить логирование в MES, CRM и RabbitMQ-интеграции;
- развернуть OpenSearch, Dashboards и Fluent Bit;
- настроить поиск по `order_id` и `correlation_id`.

### Этап 2. Расширение покрытия
- подключить онлайн-магазин и внешний API;
- добавить инфраструктурные логи;
- настроить индексы, retention и роли доступа.

### Этап 3. Аналитика и алертинг
- настроить алерты;
- добавить аномалии и saved searches;
- связать логи с трейсингом и метриками.

## Итог
Для «Александрита» логирование должно стать централизованной системой анализа инцидентов, а не просто набором текстовых файлов. Приоритет — MES, CRM, RabbitMQ и внешний API. Оптимальный путь — структурированные JSON-логи, единые идентификаторы `order_id` / `correlation_id` / `trace_id`, централизованный сбор через Fluent Bit и анализ в OpenSearch. Это сократит время расследования, повысит прозрачность прохождения заказа и снизит бизнес-риски, связанные с потерянными и просроченными заказами.
