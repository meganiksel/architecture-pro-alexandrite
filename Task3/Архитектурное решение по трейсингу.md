# Архитектурное решение по трейсингу

## Контекст
В «Александрите» заказ проходит через несколько систем и несколько типов взаимодействий:
- пользовательские запросы в онлайн-магазин;
- внутренние вызовы между компонентами приложений;
- асинхронные сообщения через RabbitMQ между CRM и MES;
- внешний API для партнёров;
- длительные операции расчёта стоимости и производственного исполнения.

Сейчас команда видит только отдельные симптомы: жалобы клиентов, жалобы операторов, просрочки и потерянные заказы. При этом нет инструмента, который позволял бы восстановить путь конкретного заказа по всем системам и понять:
- где заказ находится сейчас;
- на каком шаге он завис;
- какое сообщение не дошло или не было обработано;
- сколько времени занял каждый этап.

Для решения этой проблемы нужен distributed tracing.

## Какие системы и точки нужно покрыть трейсингом
Трейсингом нужно покрыть все точки, где заказ может потеряться, зависнуть или существенно замедлиться.

### 1. Онлайн-магазин
Покрыть:
- создание заказа;
- загрузку 3D-модели;
- отправку заказа (`SUBMITTED`);
- вызовы backend-компонентов, связанных с заказом;
- публикацию событий/команд в другие системы, если такие вызовы есть.

**Почему здесь возможна проблема:**
- заказ может быть создан, но не передан дальше;
- загрузка модели может завершиться частично или с ошибкой;
- пользователь может получить успешный ответ, но дальнейшая обработка не начнётся.

### 2. Внешний API для партнёров
Покрыть:
- входящие API-запросы партнёров;
- аутентифицированный контекст клиента;
- создание заказа через API;
- передачу заказа в MES/CRM;
- обработку ошибок и таймаутов.

**Почему здесь возможна проблема:**
- партнёр считает заказ принятым, но он не дошёл до внутреннего контура;
- возможны повторные запросы, таймауты, частичная обработка.

### 3. MES backend
Покрыть:
- приём заказа на расчёт стоимости;
- запуск и завершение расчёта стоимости;
- публикацию результата расчёта;
- получение заказа оператором в работу;
- смену статусов `PRICE_CALCULATED`, `MANUFACTURING_STARTED`, `MANUFACTURING_COMPLETED`, `PACKAGING`, `SHIPPED`;
- чтение списка заказов для dashboard, если нужно анализировать деградацию операторского сценария.

**Почему здесь возможна проблема:**
- расчёт стоимости долгий и может зависать;
- MES — критический узел процесса;
- операторские действия влияют на дальнейшее прохождение заказа.

### 4. CRM backend
Покрыть:
- создание заказа из сообщения/события;
- подтверждение заказа к производству (`MANUFACTURING_APPROVED`);
- закрытие заказа (`CLOSED`);
- обработку входящих сообщений из RabbitMQ;
- публикацию исходящих сообщений.

**Почему здесь возможна проблема:**
- заказ может не создаться в CRM;
- статус может не обновиться;
- сообщение может быть обработано частично.

### 5. RabbitMQ
Покрыть:
- публикацию сообщений;
- получение сообщений consumer’ами;
- подтверждение обработки (`ack`);
- ошибки обработки;
- повторные попытки;
- попадание сообщений в DLQ.

**Почему здесь возможна проблема:**
- сообщения могут теряться, дублироваться или зависать;
- без трассировки сложно понять, было ли сообщение опубликовано, доставлено и обработано.

### 6. Базы данных ключевых систем
Покрыть:
- критичные запросы на создание заказа;
- обновление статусов;
- чтение списка заказов в MES;
- запись результатов расчёта стоимости.

**Почему здесь возможна проблема:**
- медленные запросы и блокировки могут выглядеть как «зависший заказ»;
- важно видеть вклад БД в общую задержку.

## Список данных, которые должны попадать в трейсинг
В трейсинг должны попадать как технические, так и бизнес-атрибуты.

### 1. Идентификаторы
- `trace_id`
- `span_id`
- `parent_span_id`
- `correlation_id`
- `order_id`
- `customer_id` или псевдонимизированный идентификатор клиента
- `partner_client_id` для B2B API
- `message_id`
- `idempotency_key` при наличии

### 2. Бизнес-контекст
- текущий статус заказа
- предыдущий статус заказа
- тип канала (`b2c`, `b2b`)
- тип изделия / категория заказа
- признак кастомного изделия
- сложность модели / bucket по полигонам
- приоритет заказа

### 3. Технический контекст запроса
- имя сервиса
- имя операции
- endpoint / route
- HTTP method
- HTTP status code
- тип транспорта (`http`, `amqp`, `db`)
- имя очереди
- имя exchange / routing key
- имя БД / таблицы / query group
- длительность операции
- результат (`success`, `error`, `timeout`, `retry`, `dlq`)

### 4. Ошибки
- тип исключения
- код ошибки
- текст ошибки без чувствительных данных
- stack trace в ограниченном виде или ссылка на лог
- число попыток обработки

### 5. Временные метки
- время начала операции
- время окончания операции
- длительность
- время ожидания в очереди
- время между сменами статусов

## Мотивация

### Почему нужно внедрить трейсинг
1. **Сквозная прозрачность заказа.**  
   Команда сможет видеть полный путь заказа через онлайн-магазин, API, CRM, MES, RabbitMQ и БД.

2. **Быстрый поиск места сбоя.**  
   Вместо ручного сопоставления логов и догадок можно будет открыть трейс заказа и увидеть, где именно произошла ошибка или задержка.

3. **Снижение числа потерянных заказов.**  
   Трейсинг позволит выявлять системные точки потери сообщений и зависания обработки.

4. **Ускорение расследования инцидентов.**  
   Сократится MTTR и нагрузка на разработчиков, поддержку и менеджеров.

5. **Основа для автоматического контроля SLA.**  
   На основе данных трейсинга можно строить мониторинг прохождения заказа и алертинг по зависшим этапам.

### Технические и бизнес-метрики, на которые повлияет внедрение трейсинга
1. **MTTR** — среднее время восстановления после инцидента снизится.
2. **Доля заказов с неизвестным состоянием** — должна существенно снизиться.
3. **Доля заказов, потерянных между системами** — должна снизиться после выявления проблемных переходов.
4. **Время диагностики причины просрочки заказа** — сократится.
5. **SLA выполнения заказов / доля просроченных заказов** — улучшится за счёт более раннего обнаружения проблем.

## Предлагаемое решение

### Выбранный подход
Предлагается внедрить distributed tracing на базе:
- **OpenTelemetry** как стандарта инструментирования;
- **OpenTelemetry Collector** как точки приёма, обработки и маршрутизации трейсов;
- **Jaeger** как backend и UI для хранения и анализа трейсов.

Такой стек подходит, потому что:
- он кросс-языковой и поддерживает Java, C# и фронтенд/HTTP-интеграции;
- позволяет постепенно внедрять трейсинг без жёсткой привязки к одному вендору;
- хорошо подходит для MVP и дальнейшего роста;
- совместим с будущим переходом в Kubernetes.

### Какие компоненты нужно внедрить или доработать
1. **Инструментировать backend онлайн-магазина** через OpenTelemetry SDK для Java.
2. **Инструментировать backend CRM** через OpenTelemetry SDK для Java.
3. **Инструментировать backend MES** через OpenTelemetry SDK для .NET.
4. **Инструментировать внешнее API** и все входящие запросы партнёров.
5. **Добавить propagation trace context**:
   - в HTTP-заголовках;
   - в сообщениях RabbitMQ через headers.
6. **Добавить correlation id / order id в span attributes и baggage**, где это безопасно.
7. **Развернуть OpenTelemetry Collector** как отдельный компонент.
8. **Развернуть Jaeger** для хранения и просмотра трейсов.
9. **Настроить sampling**:
   - head-based sampling для общего потока;
   - повышенный sampling для ошибок и долгих операций;
   - при необходимости tail-based sampling позже.
10. **Связать трейсинг с логированием** через общий `trace_id`.

### Как будет работать решение
1. Пользователь или партнёр инициирует заказ.
2. На входе в backend создаётся root span.
3. При каждом внутреннем вызове и публикации сообщения trace context передаётся дальше.
4. Consumer RabbitMQ извлекает trace context из headers и продолжает тот же trace.
5. Долгие операции расчёта стоимости и смены статусов создают отдельные spans.
6. Все spans отправляются в OpenTelemetry Collector.
7. Collector экспортирует данные в Jaeger.
8. Команда поддержки и разработки может найти трейс по `order_id`, `correlation_id`, `client_id` или временному диапазону.

### Какие спаны стоит создавать
- `order.create`
- `model.upload`
- `order.submit`
- `api.partner.order.accept`
- `mes.price.calculate`
- `crm.order.create`
- `crm.order.approve`
- `mes.order.pickup`
- `mes.order.complete`

- `crm.order.close`

- `db.order.insert`

- передачу trace context через RabbitMQ;

## Компромиссы
1. **Трейсинг не заменяет логи и метрики.**  
   Он показывает путь запроса, но не всегда содержит достаточно деталей для глубокого анализа ошибки.

2. **Не все компоненты одинаково легко инструментировать.**  
   Если часть MES или сторонних библиотек плохо поддерживает OpenTelemetry, потребуется дополнительная доработка.

3. **Асинхронные сценарии сложнее синхронных.**  
   Для RabbitMQ важно корректно передавать контекст и аккуратно моделировать publish/consume spans.

4. **Высокая детализация увеличивает стоимость хранения.**  
   Если трассировать всё подряд без sampling, объём данных быстро вырастет.

5. **Трейсинг не всегда полезен для очень длинных бизнес-процессов без промежуточной инструментированной логики.**  
   Если между этапами есть ручные действия операторов или внешние офлайн-процессы, часть задержки будет видна только как большой интервал между событиями.

6. **Проприетарные или трудно изменяемые компоненты могут ограничить полноту решения.**  
   Если часть купленного MES-кода сложно доработать, покрытие может быть неполным на первом этапе.

## Безопасность

### Внутри компании
1. Доступ к Jaeger UI должен быть только у сотрудников с актуальной учётной записью.
2. Нужна интеграция с корпоративной аутентификацией (SSO/IdP), если она есть.
3. Доступ должен быть ролевым:
   - поддержка — просмотр трейсов;
   - разработчики — просмотр и технический анализ;
   - администраторы платформы — настройка Collector и backend.
4. Все обращения к UI и API системы трейсинга должны идти по HTTPS/TLS.
5. Доступ к Collector должен быть ограничен сетевыми политиками / security groups.

### Снаружи
1. Jaeger UI не должен быть доступен публично без VPN, bastion или корпоративного reverse proxy.
2. Внешние партнёры не должны иметь прямой доступ к данным трейсов.
3. Trace-данные не должны содержать чувствительные персональные данные в открытом виде.

### Работа с чувствительными данными
1. Не передавать в span attributes:
   - ФИО;
   - адреса;
   - платёжные данные;
   - содержимое файлов 3D-моделей;
   - токены и секреты.
2. Использовать псевдонимизированные идентификаторы клиентов.
3. Настроить фильтрацию и redaction чувствительных полей в Collector.
4. Ограничить срок хранения трейсов в соответствии с задачами расследования и требованиями безопасности.

## План внедрения

### Этап 1. MVP
- Инструментировать входящие HTTP-запросы в онлайн-магазине, CRM и MES.
- Добавить trace context propagation между сервисами.
- Инструментировать RabbitMQ publish/consume.
- Развернуть OpenTelemetry Collector и Jaeger.
- Научиться искать трейс по `order_id`.

### Этап 2. Расширение покрытия
- Добавить спаны для расчёта стоимости, смены статусов и критичных DB-запросов.
- Связать трейсинг с логами через `trace_id`.
- Настроить sampling и retention.

### Этап 3. Автоматизация
- Построить trace-based monitoring по зависшим заказам.
- Настроить алертинг.
- Добавить дашборды по длительности этапов заказа.

## Итог
Distributed tracing для «Александрита» должен покрыть весь путь заказа через онлайн-магазин, API, CRM, MES, RabbitMQ и критичные обращения к БД. Оптимальный путь — внедрение OpenTelemetry + Collector + Jaeger с передачей trace context через HTTP и RabbitMQ. Это даст команде прозрачность прохождения заказа, ускорит расследование инцидентов и создаст основу для автоматического контроля зависших заказов.
