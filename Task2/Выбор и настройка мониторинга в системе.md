# Выбор и настройка мониторинга в системе

## Контекст
Система «Александрит» состоит из трёх основных приложений:
- онлайн-магазин на Vue + Java Spring Boot;
- CRM на Vue + Java Spring Boot;
- MES на React + C#.

Также в ландшафте есть RabbitMQ для интеграции CRM и MES, внешнее API для партнёров, базы данных в Yandex Cloud Managed Services и пользовательские сценарии B2C и B2B. После открытия API нагрузка выросла, а Яндекс Метрика перестала отражать полную картину, потому что:
- она покрывает в основном веб-поведение пользователей;
- не показывает состояние внутренних сервисов и очередей;
- не покрывает B2B-заказы, приходящие через API;
- не позволяет контролировать прохождение заказа по распределённому процессу.

Поэтому компании нужен полноценный технический и бизнес-мониторинг.

## Мотивация
Внедрение мониторинга нужно по следующим причинам:

1. **Раннее обнаружение проблем.**  
   Сейчас команда узнаёт о сбоях от клиентов и операторов. Мониторинг позволит видеть деградацию до того, как она приведёт к жалобам и потере контрактов.

2. **Снижение числа потерянных и зависших заказов.**  
   Если отслеживать очереди, ошибки интеграции, время прохождения заказа между статусами и длительность расчёта стоимости, можно быстро находить узкие места и реагировать до нарушения SLA.

3. **Повышение прозрачности для бизнеса.**  
   Бизнесу нужны ответы на вопросы: сколько заказов зависло, где именно они застревают, сколько времени занимает расчёт стоимости, сколько заказов приходит через API, какова доля просрочек. Мониторинг даст эти ответы в виде дашбордов и алертов.

4. **Основа для масштабирования.**  
   Без метрик невозможно обоснованно масштабировать сервисы, базы, очереди и инфраструктуру. Мониторинг нужен для capacity planning.

5. **Сокращение времени восстановления.**  
   При наличии метрик и алертов команда быстрее локализует проблему, снижая MTTR и нагрузку на поддержку.

### Что это даст компании
- снижение числа просроченных заказов;
- снижение числа потерянных заказов;
- уменьшение времени реакции на инциденты;
- повышение стабильности API для партнёров;
- возможность обосновывать инфраструктурные и продуктовые решения цифрами.

## Выбор подхода к мониторингу
Для разных частей системы стоит использовать разные подходы.

### 1. RED для пользовательских и интеграционных сервисов
Подход RED (`Rate`, `Errors`, `Duration`) подходит для:
- backend онлайн-магазина;
- backend CRM;
- backend MES;
- внешнего API;
- интеграционных HTTP/gRPC вызовов между сервисами, если они появятся;
- обработчиков сообщений, если трактовать обработку сообщения как запрос.

**Почему RED:**
- хорошо показывает здоровье сервисов, которые принимают запросы;
- позволяет быстро увидеть рост нагрузки, ошибок и задержек;
- прост для внедрения и интерпретации.

### 2. USE для инфраструктурных компонентов
Подход USE (`Utilization`, `Saturation`, `Errors`) подходит для:
- RabbitMQ;
- баз данных;
- виртуальных машин / инстансов;
- дисков, CPU, памяти, сети;
- Kubernetes в будущем.

**Почему USE:**
- помогает понять, упирается ли система в ресурсы;
- особенно полезен для анализа деградации MES dashboard и тяжёлого расчёта стоимости;
- позволяет заранее увидеть насыщение ресурсов.

### 3. Дополнительный бизнес-мониторинг поверх технических метрик
Ни RED, ни USE не покрывают полностью бизнес-процесс заказа, поэтому дополнительно нужен слой **business metrics**:
- число заказов по статусам;
- время между статусами;
- число зависших заказов;
- доля заказов, не дошедших до следующего этапа за допустимое время;
- доля заказов API-партнёров с нарушением SLA.

## Какие метрики отслеживать

Ниже перечислены ключевые метрики по слоям системы.

---

## 1. Онлайн-магазин

### 1.1 HTTP requests total
**Зачем нужна:** показывает интенсивность входящего трафика по пользовательским операциям: создание заказа, загрузка модели, отправка заказа.

**Ярлыки:**
- `service=shop-backend`
- `endpoint`
- `method`
- `status_code`
- `channel` (`b2c-web`, если позже появятся другие каналы)

### 1.2 HTTP request duration
**Зачем нужна:** позволяет видеть деградацию пользовательских операций, особенно загрузки модели и отправки заказа.

**Ярлыки:**
- `service`
- `endpoint`
- `method`
- `status_class`

### 1.3 HTTP errors total
**Зачем нужна:** показывает рост ошибок на критичных пользовательских сценариях.

**Ярлыки:**
- `service`
- `endpoint`
- `error_type`
- `status_code`

### 1.4 Orders created total
**Зачем нужна:** бизнес-метрика числа новых заказов, помогает сравнивать входящий поток с количеством реально обработанных заказов.

**Ярлыки:**
- `channel` (`b2c`, `b2b`)
- `source`
- `product_type`

### 1.5 3D model upload size / upload failures
**Зачем нужна:** помогает понять, влияют ли большие модели на деградацию и ошибки загрузки.

**Ярлыки:**
- `file_type`
- `channel`
- `customer_type`

## 2. CRM backend

### 2.1 HTTP requests total / duration / errors
**Зачем нужна:** базовый RED-мониторинг CRM API.

**Ярлыки:**
- `service=crm-backend`
- `endpoint`
- `method`
- `status_code`

### 2.2 Orders approved total
**Зачем нужна:** показывает, сколько заказов реально подтверждается к производству.

**Ярлыки:**
- `channel`
- `manager_id` или `team`
- `customer_segment`

### 2.3 Order status transition total
**Зачем нужна:** позволяет видеть, как часто происходят переходы между статусами и где процесс тормозится.

**Ярлыки:**
- `from_status`
- `to_status`
- `channel`
- `source_system`

### 2.4 Time in status
**Зачем нужна:** ключевая бизнес-метрика. Показывает, сколько заказ находится в конкретном статусе.

**Ярлыки:**
- `status`
- `channel`
- `customer_segment`

## 3. MES backend

### 3.1 HTTP requests total / duration / errors
**Зачем нужна:** базовый RED-мониторинг MES API и операторских сценариев.

**Ярлыки:**
- `service=mes-backend`
- `endpoint`
- `method`
- `status_code`

### 3.2 Dashboard query duration
**Зачем нужна:** отдельная метрика для первой страницы MES, так как это явно проблемный сценарий.

**Ярлыки:**
- `filter_status`
- `page`
- `operator_role`

### 3.3 Price calculation duration
**Зачем нужна:** одна из самых важных метрик. Позволяет видеть среднее, p95, p99 время расчёта стоимости.

**Ярлыки:**
- `model_complexity_bucket`
- `polygon_bucket`
- `channel`
- `customer_segment`

### 3.4 Price calculation queue length
**Зачем нужна:** показывает накопление заказов на расчёт стоимости.

**Ярлыки:**
- `priority`
- `channel`

### 3.5 Manufacturing started/completed total
**Зачем нужна:** показывает throughput производства на уровне ИТ-системы.

**Ярлыки:**
- `operator_id` или `team`
- `product_type`
- `channel`

### 3.6 Orders waiting for operator pickup
**Зачем нужна:** показывает, сколько заказов доступны, но ещё не взяты в работу.

**Ярлыки:**
- `status`
- `priority`
- `channel`

## 4. RabbitMQ

### 4.1 Queue depth
**Зачем нужна:** показывает накопление сообщений и потенциальное отставание обработки.

**Ярлыки:**
- `queue_name`
- `message_type`
- `producer`
- `consumer`

### 4.2 Publish rate / consume rate
**Зачем нужна:** позволяет сравнивать скорость публикации и обработки сообщений.

**Ярлыки:**
- `queue_name`
- `message_type`

### 4.3 Unacked messages
**Зачем нужна:** показывает зависшие в обработке сообщения.

**Ярлыки:**
- `queue_name`
- `consumer_group` или `consumer_service`

### 4.4 DLQ messages total
**Зачем нужна:** критическая метрика для обнаружения проблем интеграции.

**Ярлыки:**
- `queue_name`
- `message_type`
- `error_type`

### 4.5 Consumer errors total
**Зачем нужна:** показывает ошибки обработки сообщений.

**Ярлыки:**
- `consumer_service`
- `queue_name`
- `exception_type`

## 5. Базы данных

### 5.1 Query latency
**Зачем нужна:** помогает находить медленные запросы, особенно для MES dashboard и операций смены статусов.

**Ярлыки:**
- `db_name`
- `operation` (`select`, `insert`, `update`)
- `query_group`
- `service`

### 5.2 Connections active
**Зачем нужна:** показывает, не упирается ли приложение в лимиты соединений.

**Ярлыки:**
- `db_name`
- `service`

### 5.3 CPU / memory / disk / IOPS
**Зачем нужна:** базовый USE-мониторинг БД.

**Ярлыки:**
- `db_name`
- `instance_role`

### 5.4 Lock wait / deadlocks
**Зачем нужна:** помогает выявлять проблемы конкурентного доступа.

**Ярлыки:**
- `db_name`
- `service`

### 5.5 Replication lag
**Зачем нужна:** если будет использоваться чтение с реплики, важно контролировать отставание.

**Ярлыки:**
- `db_name`
- `replica`

## 8. Бизнес-метрики сквозного процесса

### 8.1 Orders in status
**Зачем нужна:** показывает текущее распределение заказов по статусам.

**Ярлыки:**
- `status`
- `channel`
- `customer_segment`

### 8.2 Orders stuck total
**Зачем нужна:** ключевая метрика для поиска зависших заказов.

**Ярлыки:**
- `status`

- `threshold_bucket`

### 8.3 End-to-end order lead time
**Зачем нужна:** показывает полное время прохождения заказа от создания до закрытия.

- `last_known_status`

## Дополнительные метрики, которые стоит добавить
1. **Error budget burn rate** для критичных API и внутренних сервисов.
2. **Deployment frequency** и **change failure rate** — для оценки влияния релизного процесса на стабильность.
3. **MTTR** — среднее время восстановления после инцидента.
4. **Consumer lag by queue age** — возраст самого старого необработанного сообщения.
5. **Order recalculation count** — сколько раз заказ пересчитывался по стоимости, чтобы видеть нестабильные сценарии.

## Технологический стек мониторинга
Предлагаемый стек:
- **Prometheus** — сбор и хранение метрик;
- **Grafana** — дашборды и визуализация;
- **Alertmanager** — маршрутизация алертов;
- **Экспортеры**:
  - Node Exporter для VM;
  - RabbitMQ Exporter;
  - PostgreSQL/MySQL exporter в зависимости от используемой БД;
  - JVM metrics через Micrometer / Spring Boot Actuator для Java-сервисов;
  - OpenTelemetry Metrics / Prometheus exporter для C# MES;
- **Yandex Cloud Monitoring** можно использовать как дополнительный источник инфраструктурных метрик, если это удобнее для managed-сервисов.

## План действий
Ниже — высокоуровневый драфт технического задания.

1. Создать контур мониторинга для dev/release/prod с разделением доступов.
2. Развернуть Prometheus, Grafana и Alertmanager.
3. Подключить инфраструктурные экспортеры для VM, RabbitMQ и баз данных.
4. Подключить application metrics:
   - для Java-сервисов через Micrometer + Prometheus endpoint;
   - для C# MES через OpenTelemetry / Prometheus exporter.
5. Добавить бизнес-метрики в код сервисов:
   - переходы статусов;
   - время в статусе;
   - длительность расчёта стоимости;
   - число зависших заказов;
   - SLA breach.
6. Настроить единый набор ярлыков:
   - `service`, `environment`, `channel`, `status`, `client_id`, `queue_name`, `source_system`.
7. Создать дашборды:
   - executive dashboard для бизнеса;
   - operational dashboard для поддержки и тимлида;
   - service dashboards для разработчиков;
   - dashboard очередей и интеграций;
   - dashboard MES performance.
8. Настроить алерты:
   - рост 5xx;
   - рост latency p95/p99;
   - рост DLQ;
   - рост глубины очередей;
   - зависшие заказы;
   - нарушение SLA;
   - деградация dashboard MES;
   - насыщение CPU/RAM/DB connections.
9. Настроить регламент реакции на алерты:
   - кто получает уведомление;
   - в какие каналы отправляется алерт;
   - какие runbook используются.
10. Провести baseline-замеры и зафиксировать текущие значения до оптимизаций.
11. Через 2–4 недели после внедрения пересмотреть пороги и состав метрик.

## Обоснование для бизнеса
Мониторинг — это не «техническая роскошь», а инструмент защиты выручки и репутации.

### Почему бизнесу стоит выделить ресурсы
1. **Снижение потерь контрактов.**  
   Сейчас компания уже теряет крупных клиентов. Мониторинг позволит быстрее выявлять и устранять причины просрочек.

2. **Снижение нагрузки на поддержку и менеджеров.**  
   Вместо ручного выяснения «где заказ» команда сможет быстро видеть проблему по дашбордам.

3. **Повышение прозрачности B2B API.**  
   Для партнёров важно соблюдать SLA. Без мониторинга невозможно управлять качеством API-канала.

4. **Основа для масштабирования бизнеса.**  
   Компания выходит на новые рынки. Без мониторинга рост нагрузки будет и дальше приводить к деградации.

5. **Более точные инвестиции.**  
   Метрики покажут, куда действительно нужно вкладываться: в БД, очереди, MES, API или команду.

## Дополнительное задание: показатели насыщенности

### Показатели насыщенности

#### 1. CPU utilization > 75% sustained 15 min
**Почему:** при длительной загрузке выше 75% система теряет запас на пики.

**Что делать:**
- создать тикет на анализ;
- если превышение на prod и есть риск деградации — масштабировать инстанс или добавить реплику/инстанс;
- уведомить DevOps/SRE.

#### 2. DB connections > 80% лимита
**Почему:** близость к лимиту соединений быстро приводит к отказам приложений.

**Что делать:**
- алерт в поддержку и DevOps;
- анализ connection pool;
- при необходимости временное ограничение нагрузки на API.

#### 3. Queue depth растёт 10+ минут и consume rate < publish rate
**Почему:** это признак отставания обработки и будущих задержек заказов.

**Что делать:**
- завести инцидент;
- проверить consumer errors;
- при необходимости увеличить число consumers или ограничить входящий поток.

#### 4. Price calculation p95 > 10 минут, p99 > 20 минут
**Почему:** расчёт стоимости — критичный этап, напрямую влияющий на срок обработки заказа.

**Что делать:**
- уведомить команду разработки и поддержки;
- проверить очередь расчёта и ресурсы MES;
- при систематическом превышении — запуск инициативы по выделению расчётного контура.

#### 5. Orders stuck total выше порога
Порог можно задать так:
- более 20 заказов без движения > 30 минут на ранних этапах;
- более 10 заказов без движения > 4 часов на производственных этапах.

**Почему:** это уже прямой бизнес-риск.

**Что делать:**
- автоматически создавать тикет;
- отправлять уведомление в канал поддержки/операций;
- при массовом характере — эскалировать тимлиду и продакт-менеджеру.

## Итог
Для «Александрита» мониторинг должен покрывать не только инфраструктуру и API, но и сам бизнес-процесс прохождения заказа. Оптимальный подход — сочетание RED для сервисов, USE для инфраструктуры и отдельного слоя бизнес-метрик. Это позволит компании перейти от реактивного управления по жалобам к проактивному управлению качеством сервиса и масштабированием.
